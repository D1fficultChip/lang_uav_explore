# 下一步技术设计方案

## 1. 设计目标

基于当前系统已有工作与 `Benchmark设计草案2.0`，下一步技术推进不再以“继续堆功能”为目标，而是以：

- 支撑 `Outcome / Process / Closed-loop Reasoning & Recovery / Generalization & Robustness`
- 支撑 `Episode / Stage / Runtime Event` 三层评价
- 保持中枢层作为高层智能执行器
- 保持底层 skill 作为可靠能力承载

为核心目标。

一句话概括：

**下一步要做的不是更多功能，而是把当前系统重构成“可评测、可解释、可编排”的 skill-centric verified runtime。**

---

## 2. 当前已有基础

当前项目已经具备以下基础：

### 2.1 Runtime 基础

- `WorldState`
- `Verifier`
- `Diagnostics`
- `Recovery`
- `Progress / Milestone`
- `Reasoner`

### 2.2 感知基础

- GSAM2 已支持 richer proposal
- semantic verification 框架已接入

### 2.3 任务编译基础

- Qwen-based constrained task compiler 已存在
- `plan.json` 中已有：
  - `entities`
  - `relations`
  - `stages`
  - `transitions`
  - `assumptions`
  - `open_questions`

### 2.4 底层 skill 基础

- SEARCH -> FALCON
- NAVIGATE -> EGO
- HOLD / TRACK -> runtime 当前已有基础控制路径

因此，下一步不需要从零搭架构，而是要做“对齐”和“收敛”。

---

## 3. 下一步的总技术路线

建议下一步按四个技术包推进：

1. `Schema & Runtime Alignment`
2. `Skill Contract Layer`
3. `Closed-loop Verification Package`
4. `Benchmark Instrumentation & Evaluator`

这四个技术包是下一阶段最关键的骨架。

---

## 4. 技术包 A：Schema & Runtime Alignment

## 4.1 目标

当前 benchmark 2.0 强调“正确推进”，这要求：

- 编译器输出的 plan 语义
- runtime 实际能理解的条件
- verifier 实际能判断的证据

三者必须一致。

## 4.2 当前主要问题

虽然 compiler 和 runtime 已经都存在，但仍有未完全对齐的地方，例如：

- runtime `ConditionEngine` 支持的事件类型有限
- plan 中某些 richer 条件还不能被 runtime 真正消费
- relation / semantic support 仍未正式进入 condition 判定

## 4.3 下一步改造目标

把 plan schema 分成两层：

### `Compiled Plan`

来自 task compiler，包含较丰富语义：

- entities
- relations
- assumptions
- open_questions
- stages
- transitions

### `Runtime Plan`

在 runtime 启动时，对 compiled plan 进行一次规范化：

- 映射 unsupported intents
- 展平/规范事件条件
- 把 success/failure/transitions 编译成 runtime 可判定规则

## 4.4 具体改造建议

建议新增：

- `central_runtime_v0/central_runtime/runtime_plan.py`
- `central_runtime_v0/central_runtime/plan_compiler_runtime.py`

建议修改：

- [/home/young/uav_demo/central_runtime_v0/central_runtime/plan_loader.py](/home/young/uav_demo/central_runtime_v0/central_runtime/plan_loader.py)
- [/home/young/uav_demo/central_runtime_v0/central_runtime/conditions.py](/home/young/uav_demo/central_runtime_v0/central_runtime/conditions.py)

## 4.5 本包产出

- 一套 runtime 可执行 plan 规范
- 一套“正确推进”的可判定标准
- 为 benchmark 的 Stage 级指标提供统一依据

## 5. 技术包 B：Skill Contract Layer

## 5.1 目标

将已有模块正式统一成 skill，使中枢层的大模型真正做“skill executive”。

## 5.2 为什么这一包最关键

没有 skill contract，就很难稳定评估：

- skill 是否调用合理
- skill 是否切换合理
- recovery 是否正确
- 哪个模块在什么时刻真正起作用

而这些正是 benchmark 2.0 里的核心指标。

## 5.3 推荐 skill 列表

先把当前已有能力统一包装成这些 skill：

- `FastProposalSkill`
- `SemanticVerifySkill`
- `SearchSkill`
- `NavigateSkill`
- `HoldObserveSkill`

后续扩展时再加：

- `LocalizeTargetSkill`
- `TrackDynamicTargetSkill`

## 5.4 Skill Contract 设计

建议新增：

- `central_runtime_v0/central_runtime/skills/contracts.py`
- `central_runtime_v0/central_runtime/skills/registry.py`
- `central_runtime_v0/central_runtime/skills/results.py`
- `central_runtime_v0/central_runtime/skills/base.py`

每个 skill 至少定义：

- `skill_id`
- `intent`
- `inputs`
- `outputs`
- `preconditions`
- `success_signals`
- `failure_signals`
- `recoverability`
- `safe_stop`

## 5.5 与现有代码的关系

现有 `adapters` 保留不动，skill contract 在其上层包装即可。

建议先包：

- `/central_runtime/adapters/falcon_search.py`
- `/central_runtime/adapters/ego_navigate.py`
- `/central_runtime/semantic_verifier.py`
- GSAM2 输出链

## 5.6 本包产出

- 中枢层从“调模块”升级成“调 skill”
- 为 `Unnecessary Skill Switch Rate` 等指标提供清晰边界
- 为未来 `TrackDynamicTargetSkill` 和 `LocalizeTargetSkill` 预留位置

## 6. 技术包 C：Closed-loop Verification Package

## 6.1 目标

把“闭环智能”真正做成 benchmark-ready 的技术主线。

## 6.2 需要补的三块

### C1. Explicit Verify Stage

当前系统已有：

- hold
- retry
- semantic verification

但还没有真正的：

- `Verify Stage`

建议新增：

- runtime 支持插入显式 verify stage
- verify stage 只做：
  - reobserve
  - semantic verify
  - focused proposal refresh

这一步直接支撑：

- `Premature Progression Rate`
- `Evidence-Insufficient Progression Rate`

### C2. Temporal Verification

当前验证仍偏单次事件驱动，建议增加：

- 近期 proposal consistency
- semantic support count
- cue persistence
- evidence aggregation

建议新增：

- `central_runtime_v0/central_runtime/evidence_aggregator.py`
- 或 `temporal_verifier.py`

### C3. Relation-aware Verification

当前 relation 主要还停留在 plan 和 summarizer 层，建议做一个轻量版本：

- 先不做强几何关系
- 先做 semantic + 2D/cue weak relation verification

例如：

- `near`
- `around`
- `with`

## 6.3 具体改造建议

建议新增：

- `central_runtime_v0/central_runtime/verifiers/semantic.py`
- `central_runtime_v0/central_runtime/evidence_aggregator.py`

建议修改：

- [/home/young/uav_demo/central_runtime_v0/central_runtime/executor.py](/home/young/uav_demo/central_runtime_v0/central_runtime/executor.py)
- [/home/young/uav_demo/central_runtime_v0/central_runtime/world_state.py](/home/young/uav_demo/central_runtime_v0/central_runtime/world_state.py)

## 6.4 本包产出

- 闭环验证从“框架存在”升级成“机制完整”
- 为 benchmark 的 Runtime Event 级指标提供真实支撑

## 7. 技术包 D：Benchmark Instrumentation & Evaluator

## 7.1 目标

让 benchmark 2.0 中的指标变成真实可计算指标，而不是文档上的描述。

## 7.2 为什么必须做这一包

如果没有统一日志和 evaluator，后面你只能：

- 手工看录像
- 手工解释任务是否成功
- 手工判断是否推进错误

这无法形成严肃 benchmark。

## 7.3 建议新增三层日志

### Episode 级日志

记录：

- 任务 id
- 指令
- budget
- 最终状态
- completion time

### Stage 级日志

记录：

- stage enter / exit
- success / failure
- transition cause
- stage budget usage

### Runtime Event 级日志

记录：

- proposal generated
- semantic verify called
- verification accepted / rejected
- recovery started / finished
- skill invoked / switched / retried
- reasoner proposal / guard result

## 7.4 具体建议

建议新增：

- `central_runtime_v0/central_runtime/runtime_events.py`
- `central_runtime_v0/central_runtime/eval_schema.py`
- `tools/eval_runtime_logs.py`
- `tools/benchmark_runner.py`

建议修改：

- [/home/young/uav_demo/central_runtime_v0/central_runtime/executor.py](/home/young/uav_demo/central_runtime_v0/central_runtime/executor.py)

## 7.5 第一批可计算指标

建议优先做这些：

### Episode 级

- `Task Success Rate`
- `Within-Budget Success Rate`
- `Completion Time`

### Stage 级

- `Stage Completion Accuracy`
- `Correct Transition Rate`
- `Premature Progression Rate`

### Runtime Event 级

- `Verification Precision / Recall`
- `Recovery Success Rate`
- `Failure Diagnosis Accuracy`

---

## 8. 建议实施顺序

建议按以下顺序推进，不建议并行过多开发：

### Step 0：Compiler / Runtime 对齐修正

包括：

- 修正 `task_compiler_v0.py` 当前语法问题
- 对齐 compiler event vocab 与 runtime event support

### Step 1：Skill Contract Layer

先把当前已有能力 skill 化。

### Step 2：Benchmark Instrumentation

把 Episode / Stage / Runtime Event 三层日志打通。

### Step 3：Verify Stage + Temporal Verification

补足闭环验证机制。

### Step 4：Relation-aware Verification

支撑更强任务族。

### Step 5：之后再接更底层新 skill

例如：

- `TrackDynamicTargetSkill`
- `LocalizeTargetSkill`

---

## 9. 当前不建议做的事情

为了避免再次“盲目堆功能”，当前不建议优先做：

- 过早实现几何大模块
- 过早实现强耦合 spatial planner
- 让中枢层直接承担 tracking / localization / low-level planning
- 在没有 benchmark 约束的前提下继续添加零散功能

---

## 10. 默认执行方案

如果按这份设计继续开工，我建议默认下一步就做：

1. `Step 0`
- 修编译器语法问题
- 对齐 compiler/runtime schema

2. `Step 1`
- 新增 skill contract
- 包装已有 skill

3. `Step 2`
- 新增 benchmark evaluator 所需日志结构

这三步做完之后，系统会进入一个很好的状态：

- 架构清晰
- 中枢职责明确
- benchmark 可开始真实计算
- 后续加底层 skill 不会返工

---

## 11. 当前结论

基于 benchmark 2.0 和当前已有代码，下一步最合理的技术推进不是继续加能力，而是：

- 先做 `Schema 对齐`
- 再做 `Skill Contract`
- 再做 `Benchmark Instrumentation`
- 最后围绕 benchmark 指标补 `Verify / Temporal / Relation`

这会让后续所有开发都服务于一个清晰目标：

**构建一个可验证、可编排、可评测的真实 UAV language agent runtime。**

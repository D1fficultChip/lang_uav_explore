# 中枢层智能化机制说明

## 1. 说明目的

本文档用于解释当前系统中“中枢层智能化”具体是如何实现的，尤其说明：

- 中枢层中的大模型处于什么位置
- 它会对哪些信息进行推理
- 它会给出哪些高层建议
- 它如何驱动中枢层进行调度
- 它不会做什么

需要强调的是，当前系统中的中枢层智能化，并不是让大模型直接控制无人机，而是让大模型以**受约束认知增强模块**的形式嵌入 `central runtime`，增强高层任务执行能力。

也就是说，中枢层并不等于某一个文件，而是一套负责：

- 执行任务图
- 维护状态

- 做验证
- 做恢复
- 做高层语义推理

## 3. 中枢层中的大模型位于哪里

当前中枢层中，大模型主要位于两类模块里：

### 3.1 语义验证模块

对应代码：

- [semantic_verifier.py](/home/young/uav_demo/central_runtime_v0/central_runtime/semantic_verifier.py)

其定位是：

- 对当前 proposal 和任务上下文做语义验证
- 判断当前证据是否支持当前目标
- 在证据不足时给出保守 followup 建议

这是当前中枢层里已经最明确、最实用、最直接参与运行时推理的 LLM 模块。

### 3.2 运行时 reasoner 模块

对应代码：

- [llm_reasoner.py](/home/young/uav_demo/central_runtime_v0/central_runtime/reasoner/llm_reasoner.py)
- [state_summarizer.py](/home/young/uav_demo/central_runtime_v0/central_runtime/reasoner/state_summarizer.py)
- [guard.py](/home/young/uav_demo/central_runtime_v0/central_runtime/reasoner/guard.py)

其定位是：

- 面向整个运行时状态做高层推理
- 给出阶段级 / skill 级 / recovery 级建议

这一层已经接好了接口，但默认可按配置启停。

## 4. 中枢层里的大模型会看哪些信息

大模型在中枢层中不是直接读原始 ROS topic 或控制量，而是读**结构化的中枢层摘要**。

### 4.1 语义验证时使用的信息

semantic verifier 会读取如下信息：

- 当前 `req_id`
- 当前 `stage_id`
- 当前 `entity_id`
- 当前 `query_type`
- 当前 primary prompt
- 当前 cue prompts
- 当前 `topk_candidates`
- 当前 `relations`
- 当前 `assumptions`
- 当前 `open_questions`
- 当前 runtime context
- 可选图像或可视化图像

这意味着它并不是简单根据一个 bbox 判定，而是在任务上下文中判断：

- 当前目标是否成立
- 当前证据是否足够
- 当前 relation 是否成立
- 当前失败更像什么原因

### 4.2 运行时 reasoner 使用的信息

runtime reasoner 读取的是更高层的运行时摘要，包括：

- 当前任务 instruction
- 当前 `stage`
- 当前 active entity
- 当前 `skill`
- 当前 milestones
- verifier 结果
- semantic verifier 结果
- diagnostics
- recent detections
- cue support
- localization 状态
- observe / track 状态
- recovery 候选动作
- `relations / assumptions / open_questions`

也就是说，它看的不是某一个模块的输出，而是整个运行时状态的压缩表示。

## 5. 中枢层里的大模型会推理什么

### 5.1 语义验证层面的推理

semantic verifier 主要推理这些问题：

- 当前 proposal 是否真的支持当前 primary target
- 当前 relation 是否成立
- 当前证据是否只是“有点像”
- 当前失败更像是遮挡、误检、背景混淆还是目标不存在
- 是否需要补观察
- 是否建议切 cue
- 是否建议 fallback

对应输出通常包括：

- `verify_status`
- `supports_primary_target`
- `supports_relation`
- `scene_consistency`
- `failure_hypothesis`
- `need_additional_view`
- `verification_confidence`
- `recommended_followup`
- `explanation`

### 5.2 运行时调度层面的推理

runtime reasoner 主要推理这些问题：

- 当前阶段是否继续
- 当前是否应该进入 verify
- 当前是否该切 skill
- 当前探索模式是否该增强或回退
- 当前是否应该 fallback 到上一个 skill
- 当前是否应该终止

对应输出通常是高层 proposal，例如：

- `continue`
- `retry_same_stage`
- `hold_and_reobserve`
- `switch_cue_priority`
- `insert_verify_stage`
- `fallback_to_search`
- `safe_terminate`

## 6. 中枢层里的大模型会给出哪些建议

从当前架构看，大模型的建议主要集中在三类：

### 6.1 证据层建议

例如：

- 当前证据不够，不能推进
- 当前证据弱支持，应补观察
- 当前 relation 只得到弱支持
- 当前更像误检而不是目标

### 6.2 恢复层建议

例如：

- `hold_and_reobserve`
- `retry_same_stage`
- `fallback_to_search`
- `switch_cue_priority`

### 6.3 技能调度层建议

例如：

- 当前应该从 `SEARCH` 切到 `OBSERVE`
- 当前应该从 `OBSERVE` 回退到 `SEARCH`
- 当前应该进入 `TRACK`
- 当前探索模式应由 `bias` 升级到 `focus`

这些建议不会直接变成控制命令，而是转化为中枢层的高层调度逻辑。

## 7. 大模型如何驱动中枢层进行调度

这里是“智能化”最关键的部分。

### 7.1 它不会直接调度底层控制

大模型不会直接：

- 发布 `/ego/pos_cmd`
- 发布 `/falcon/pos_cmd`
- 发布 PX4 控制量
- 输出轨迹
- 绕过运行时约束直接命令执行

### 7.2 它会通过中枢层驱动高层调度

更准确地说，大模型的作用链是：

1. 大模型读取中枢层摘要
2. 生成结构化判断或结构化建议
3. `executor` 结合：
   - `WorldState`
   - verifier
   - diagnostics
   - skill contract
   - success / failure criteria
4. 中枢层再决定是否真正执行某个动作

因此，中枢层的大模型会驱动：

- 是否推进当前 stage
- 是否抑制推进
- 是否进入 verify window
- 是否切换 cue priority
- 是否切换 skill
- 是否进入 observe / track
- 是否回退到 search
- 是否终止任务

### 7.3 Guard 与 runtime 约束的作用

在 runtime reasoner 这一层，大模型的输出还需要经过：

- [ReasonerGuard](/home/young/uav_demo/central_runtime_v0/central_runtime/reasoner/guard.py)

其作用是：

- 只允许白名单动作
- 不允许越权
- 不允许跳到未知 stage
- 不允许绕过安全骨架

所以最终执行是：

**LLM 建议 + runtime 状态 + verifier + guard + skill contract 的联合结果**

而不是单纯 LLM 说了算。

## 8. 一个典型例子

任务：

**“进入厂房，搜索靠近出口标识的可疑背包；发现后先靠近观察确认；若目标开始移动则持续跟踪。”**

### 8.1 任务开始

任务编译器先将自然语言任务转成结构化 plan：

- `S1: SEARCH suspicious_bag`
- cue: `exit_sign`
- `S2: OBSERVE suspicious_bag`
- `S3: TRACK suspicious_bag`

### 8.2 搜索阶段

中枢层进入 `SEARCH`：

- 写 `perception_request.json`
- 让 GSAM2 做 proposal
- 让 FALCON 进入带语义模式的搜索

### 8.3 proposal 出现但歧义较高

GSAM2 返回两个相近候选：

- candidate 1: 背包
- candidate 2: 黑色箱体

这时：

- verifier 认为证据不足
- semantic verifier 读取当前任务上下文与 top-k proposal
- 大模型输出：
  - `verify_status = weakly_supported`
  - `need_additional_view = true`
  - `recommended_followup = observe`

### 8.4 中枢层调度 ObserveSkill

中枢层不会贸然推进，而是：

- 结合 verifier 结果
- 结合 semantic verifier 输出
- 判断当前应进入 `ObserveSkill`

然后：

- 读取 `target_position_world`
- 暂停 `FALCON`
- 调 `EGO` 接近观察点
- 悬停 2s
- 再次进行 proposal 与 semantic verification

### 8.5 目标开始移动

如果观察后目标成立且开始移动：

- localization 持续更新目标位置
- 中枢判断当前应进入 `TRACK`
- 调度 `TrackDynamicTargetSkill`
- `TrackDynamicTargetSkill` 按门限刷新 EGO goal

### 8.6 目标短暂丢失

如果目标短暂丢失：

- 中枢不会立刻终止
- runtime 进入 `temporarily_lost`
- 若恢复失败，则 fallback 回 `SEARCH`

这个例子体现的是：

- 大模型负责高层证据解释与建议
- 中枢层负责 skill 调度与执行裁决
- 底层 skill 负责真实运动执行

## 9. 中枢层智能化的本质

如果用一句话概括当前系统中的中枢层智能化：

**中枢层中的大模型不直接控制无人机，而是通过任务理解、语义验证、失败诊断和高层调度建议，增强 central runtime 对技能调用、阶段推进和恢复回退的判断能力。**

也就是说，中枢层的智能化主要增强的是：

- 证据解释能力
- 阶段裁决能力
- 恢复与回退能力
- 技能调度能力

而不是：

- 低层控制能力
- 轨迹规划能力
- 飞行闭环控制能力

---

## 10. 当前最准确的职责边界

### 大模型负责

- 任务语义理解
- 证据语义验证
- 高层建议生成

### central runtime 负责

- 状态维护
- verifier
- diagnostics / recovery
- stage 与 skill 调度
- 大模型输出的约束执行

### 底层 skill 负责

- 搜索
- 导航
- 观察
- 动态跟踪
- 飞行控制

因此，当前系统最准确的整体表述是：

**大模型增强了 central runtime 的高层认知能力，而 central runtime 再将这种高层认知能力转化为受约束的多 skill 闭环执行。**

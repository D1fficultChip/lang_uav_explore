# 感知推理协同升级设计稿

## 1. 设计目标

本设计稿面向当前项目的下一阶段升级，目标是在不破坏现有真实 UAV 可部署骨架的前提下，把系统从：

- 自然语言任务 -> 计划编译 -> 规则执行 -> 感知检测 -> 阶段切换

升级为：

- 自然语言任务 -> 计划编译 -> fast proposal -> semantic verification -> verified runtime reasoning -> 安全执行

核心原则：

- 不改成端到端 VLA
- 不让大模型直接输出底层控制
- 保留 `central_runtime` 的规则安全骨架
- 保留 FALCON / EGO / PX4 / ROS 的底层工具链
- 增强“感知-验证-推理-恢复”闭环

---

## 2. 总体架构

### 2.1 分层结构

建议将系统明确划分为五层：

1. `Task Compilation Layer`
- 输入：自然语言任务
- 输出：结构化 `plan.json`

2. `Fast Proposal Layer`
- 以 GSAM2 为核心
- 负责开放词汇候选发现、目标 grounding、基础 mask/box 生成

3. `Semantic Verification Layer`
- 以 MLLM 或更强视觉语义模型为核心
- 负责语义验证、关系判断、歧义消解、失败原因解释

4. `Verified Runtime Layer`
- 以 `executor + world_state + verifier + reasoner + guard + recovery` 为核心
- 负责多源证据融合、阶段推进、运行时验证、bounded reasoning

5. `Skill Execution Layer`
- 以 FALCON / EGO / PX4 / ROS 桥接为核心
- 负责底层探索、导航、轨迹执行与物理控制

### 2.2 三个关键角色

建议将三类“智能能力”严格分工：

1. `GSAM2 = Fast Proposal`
- 回答“哪里可能有目标或线索”

2. `MLLM = Semantic Verification`
- 回答“这个候选是否真的支持当前任务目标”

3. `Runtime = Bounded Reasoning and Coordination`
- 回答“基于当前所有证据，下一步最合理且最安全的动作是什么”

## 3. 当前项目基础与升级入口

### 3.1 已有基础

当前项目中已经具备以下基础能力：

- `plan_loader.py` 已能读取 richer plan fields
- `executor.py` 已具备 `WorldState + verifier + recovery + reasoner` 框架
- `perception_request.json` 已作为结构化感知请求接口
- `infer.json / infer_cue.json` 已作为感知结果回传接口
- V2 已有 `state_summarizer / llm_reasoner / reasoner_guard`

### 3.2 当前瓶颈

目前感知链路仍偏薄：

- GSAM2 主要被当作开放词汇 detector 使用
- 输出仍以单 best result 为主
- 缺少 top-k proposals、proposal uncertainty、候选歧义表达
- 缺少 semantic verification 层
- runtime reasoner 目前主要消费运行时摘要，尚未消费 richer perception evidence

---

## 4. 升级主线

建议下一阶段按两条主线并行推进：

### 主线 A：把 GSAM2 从 detector 升级成 proposal layer

目标：

- 不再只输出 `found / score / bbox`
- 输出候选集合与 proposal-level metadata

### 主线 B：新增低频 semantic verification 层

目标：

- 在关键时刻调用 MLLM 对 GSAM2 候选做语义核验
- 把 semantic evidence 注入 `WorldState`
- 由 runtime reasoner 消费并做高层裁决

---

## 5. Phase A：GSAM2 Fast Proposal 升级设计

## 5.1 目标定位

GSAM2 不承担任务级推理，只承担：

- 开放词汇 proposal generation
- bbox/mask extraction
- 局部候选排序
- proposal uncertainty 信号输出

它不直接负责：

- 关系推理
- 3D 空间理解
- 任务完成语义判断
- 恢复决策

## 6. Phase B：Semantic Verification Layer 设计

## 6.1 目标定位

新增一层低频 semantic verifier，其职责不是做高频检测，而是做：

- 候选语义核验
- relation/context check
- ambiguity resolution
- negative evidence explanation
- verification recommendation

建议定位为：

**event-triggered semantic verification**

## 6.2 触发条件

建议只在以下情况下触发 semantic verification：

1. `PerceptionVerifier` 连续 `INCONCLUSIVE`
2. `proposal_status == multi_candidate_ambiguous`
3. `proposal_uncertainty` 较高
4. `success_criteria` 即将成立但仍需要确认
5. 当前 stage 涉及 `relations / assumptions`
6. diagnostics 表明可能发生误检、错对象、遮挡

## 6.3 输入设计

建议新增文件：

- `central_runtime_v0/central_runtime/semantic_verifier.py`

建议输入：

```python
SemanticVerifyRequest(
    req_id: int,
    stage_id: str,
    entity_id: str,
    query_type: str,
    frame_path: str,
    vis_path: Optional[str],
    primary_prompt: str,
    cue_prompts: List[str],
    topk_candidates: List[ProposalCandidate],
    relations: List[Relation],
    assumptions: List[str],
    open_questions: List[str],
    runtime_context: Dict[str, Any],
)
```

建议 `query_type`：

- `candidate_verify`
- `relation_verify`
- `ambiguity_resolve`
- `scene_consistency`

## 6.4 输出设计

建议 semantic verifier 输出结构化 JSON：

```json
{
  "verify_status": "supported",
  "supports_primary_target": true,
  "supports_relation": {
    "near_exit_sign": "weak"
  },
  "scene_consistency": "plausible",
  "failure_hypothesis": "partial_occlusion",
  "need_additional_view": true,
  "verification_confidence": 0.76,
  "recommended_followup": "hold_and_reobserve",
  "explanation": "candidate is visually consistent with a person, but relation to exit sign is weak"
}
```

建议核心字段：

- `verify_status`
  - `supported`
  - `weakly_supported`
  - `not_supported`
  - `inconclusive`
- `supports_primary_target`
- `supports_relation`
- `scene_consistency`
- `failure_hypothesis`
- `need_additional_view`
- `verification_confidence`
- `recommended_followup`
- `explanation`

## 6.5 后端实现建议

建议为 semantic verifier 预留可替换后端：

- `NoopSemanticVerifier`
- `APISemanticVerifier`
- `LocalSemanticVerifier`

初版建议：

- 先用 API 版 MLLM
- 只做低频调用
- 只在触发条件满足时调用

## 8. Bounded Action 设计

## 8.1 当前可执行动作

现有 runtime 已支持以下 bounded actions：

- `continue`
- `retry_same_stage`
- `hold_and_reobserve`
- `switch_cue_priority`
- `fallback_to_search`
- `safe_terminate`

## 8.2 下一阶段建议新增动作

建议新增：

- `request_semantic_verify`
- `insert_verify_stage`
- `narrow_to_candidate_region`
- `suppress_cue_interference`

### `request_semantic_verify`

作用：

- 不直接切 stage
- 触发一轮 MLLM semantic verification

### `insert_verify_stage`

作用：

- 在当前 stage 后插入一个保守的验证阶段
- 该阶段不新增未知技能
- 只允许执行：
  - hold + reobserve
  - focused detect
  - semantic verify

## 10. 分阶段实施路线

## 10.1 Version A：最小可行升级

目标：

- 不引入第二个感知模型
- 先把 GSAM2 proposal 层做厚

实施内容：

1. GSAM2 输出 `proposal_status + topk_candidates + spatial_hint + proposal_uncertainty`
2. `infer_reader` / `world_state` 接入这些字段
3. `PerceptionVerifier` 使用 richer proposal metadata
4. reasoner 可基于 proposal ambiguity 做 cue 重排与补验证建议

价值：

- 改动相对小
- 立刻增强 runtime 的认知基础

## 10.2 Version B：语义验证升级

目标：

- 新增 MLLM semantic verifier

实施内容：

1. 新增 `semantic_verifier.py`
2. 事件触发调用 MLLM
3. 输出结构化 semantic evidence
4. `WorldState` 吸收 semantic evidence
5. runtime 支持 `request_semantic_verify`

价值：

- 形成 “proposal -> semantic verification -> runtime reasoning” 闭环

## 10.3 Version C：论文增强版

目标：

- 完整形成 bounded perception-reasoning loop

实施内容：

1. 支持 `insert_verify_stage`
2. relation-aware verification
3. stage-specific trigger policy
4. replay / benchmark logging

价值：

- 最适合作为论文主方法完整版本

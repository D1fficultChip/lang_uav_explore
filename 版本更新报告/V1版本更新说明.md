# V1版本更新说明

## 1. 版本定位

本次 V1 更新的目标不是引入大模型推理，而是先把当前 `central_runtime` 从“轻量规则执行器”升级为“带世界状态、验证、进展跟踪与恢复能力的 verified runtime 基础版”。

设计原则：

- 不改变现有真实可飞的底层执行骨架
- 不改成端到端 VLA
- 不让大模型直接进入控制闭环
- 优先增强中枢层的信息利用能力、可解释性和可验证性

因此，V1 可以理解为：

**无模型的 verified runtime 基础版**

---

## 2. 为什么要做 V1

在原始版本中，系统主流程是：

自然语言任务 -> `plan.json` -> `executor` -> `prompt/perception_request` -> `infer.json` -> 条件判断 -> 切换阶段

这一流程已经能够真实运行，但存在几个问题：

1. `infer.json` 中已经包含 `req_id / stage_id / entity_id / role` 等结构化字段，但 runtime 没有真正利用。
2. `plan.json` 中的 `relations / assumptions / open_questions / success_criteria / failure_criteria` 大部分未进入运行时决策回路。
3. `executor` 更像规则触发器，而不是具备显式状态和验证逻辑的运行时。
4. `VERIFIED` 语义偏弱，更多是启发式判断，不足以支撑“verified runtime”的故事。
5. 失败处理主要依赖 timeout，缺少明确的诊断与恢复机制。

V1 的核心任务，就是先把这些结构补起来。

---

## 3. V1 的核心改动概览

V1 在中枢层内部新增了四类能力：

1. 观测结构扩展
2. 世界状态 World State
3. Verifier 验证层
4. Progress / Diagnostics / Recovery

它们共同把系统从：

- `plan -> infer -> 条件判断 -> 切阶段`

升级成：

- `plan -> observation ingestion -> world state update -> verifier -> criteria evaluation -> transition/recovery`

# V2 规划说明

## 1. V2 的定位

V2 的目标不是让大模型接管中枢层，而是：

**以“受约束认知增强”的形式，把大模型接入高层运行时 reasoning。**

V2 可以理解为：

**带 bounded LLM reasoning 的 verified runtime 增强版**

---

## 2. 为什么 V2 必须放在 V1 之后

如果在没有 `WorldState`、没有 verifier、没有 diagnostics 的情况下直接把大模型塞进 runtime，会出现几个问题：

- 大模型输入是零散日志，不稳定
- 大模型输出缺少约束，难以裁决
- runtime 没有统一状态表，很难解释“为什么接受或拒绝模型建议”
- 很容易破坏原有安全骨架

V1 已经解决了这些基础问题，所以 V2 可以把大模型放在一个更合理的位置：

- 读结构化状态
- 输出结构化建议
- 通过 verifier + guard 过滤

---

## 3. V2 计划新增能力

### 3.1 Runtime Reasoner

新增模块计划：

- `central_runtime/reasoner/base.py`
- `central_runtime/reasoner/noop.py`
- `central_runtime/reasoner/llm_reasoner.py`
- `central_runtime/reasoner/guard.py`
- `central_runtime/reasoner/state_summarizer.py`

V2 中大模型不直接发控制，而是做：

- 当前 stage 语义解释
- 证据总结
- 当前失败原因假设
- 是否需要补验证
- 是否建议切换 cue priority
- 是否建议插入 verify stage
- 是否建议 fallback

---

### 3.2 Structured Proposal Interface

大模型输出不允许是自由文本控制命令，而必须是结构化 proposal，例如：

- `assessment`
- `evidence_summary`
- `failure_hypothesis`
- `suggested_action`
- `confidence`

可接受的 `suggested_action` 只在白名单中：

- `continue`
- `retry_same_stage`
- `hold_and_reobserve`
- `switch_cue_priority`
- `insert_verify_stage`
- `fallback_to_search`
- `safe_terminate`

---

### 3.3 Reasoner Guard

V2 的关键不是“大模型能说什么”，而是“runtime 允许它做什么”。

因此需要 `ReasonerGuard` 来保证：

- 不允许大模型直接发底层控制命令
- 不允许直接写 ROS topic
- 不允许越过 verifier
- 不允许绕过 safety-critical backbone
- 不允许跳转到未知 stage / 未知 intent

---

### 3.4 更强的语义一致性检查

V2 会真正使用 V1 中已经接入的 plan 语义字段：

- `relations`
- `assumptions`
- `open_questions`

例如：

- 某个任务要求 “person near exit sign”
- 如果只看到 person 且长期没有 exit sign，可判为语义不充分
- 若某个 assumption 被明显违反，可触发恢复或验证阶段

---

### 3.5 有界重规划

V2 不做完全开放式 replanning，而做：

- bounded replan
- patch-level replan

也就是大模型只能建议：

- 插入一个 verify stage
- 修改 cue priority
- 从当前 stage fallback 到某个白名单阶段

而不是随意重写整张任务图。

---

## 4. V2 的核心价值

V2 完成后，你的系统就不再只是：

- “规则执行 + 黑盒工具”

而是：

- “规则安全骨架 + 大模型高层认知增强 + verifier 裁决”

这时方法叙事就可以清楚写成：

- rule-based runtime 保证安全与可部署
- LLM-based reasoner 提供语义解释、验证增强、诊断与 bounded replanning

这也是你和端到端 VLA 最有辨识度的区别。

---

## 5. V2 与 V1 的边界

一句话概括：

- `V1 = 让 runtime 具备状态、验证、进展和恢复基础`
- `V2 = 让大模型在不破坏安全骨架的前提下参与高层 reasoning`

因此，V2 不是替代 V1，而是建立在 V1 之上的增强层。

## 2. 当前 V2 已具备的功能

当前 V2 初版已经具备以下能力：

1. `StateSummarizer` 会把当前 runtime 的结构化状态整理成统一摘要，包括：
- 当前 mission / stage / active entity
- verifier 结果
- diagnostics
- milestones
- recent evidence
- relations / assumptions / open_questions

2. `LLMRuntimeReasoner` 可以把上述摘要发送给兼容 OpenAI Chat Completions 的大模型 API。

3. 大模型输出不会直接控制 UAV，而是必须返回结构化 proposal，字段包括：
- `assessment`
- `evidence_summary`
- `failure_hypothesis`
- `suggested_action`
- `target_stage_id`
- `confidence`
- `extra`

4. `ReasonerGuard` 会对白名单动作做审核，当前允许的动作类型由配置控制，例如：
- `continue`
- `retry_same_stage`
- `hold_and_reobserve`
- `switch_cue_priority`
- `insert_verify_stage`
- `fallback_to_search`
- `safe_terminate`

5. `executor` 已经支持在特定触发条件下调用 reasoner，例如：
- stage failure criteria 触发
- 出现 diagnostics
- verifier 出现 `INCONCLUSIVE / CONTRADICTED / FAILED`

6. 对于 guard 允许且配置为 `auto_apply` 的动作，executor 已经可以直接执行一部分安全的高层动作，包括：
- `retry_same_stage`
- `hold_and_reobserve`
- `switch_cue_priority`
- `fallback_to_search`
- `safe_terminate`

7. 当执行 `switch_cue_priority` 时，runtime 可以按新的 cue 顺序重写 `perception_request.json` 和 `cues.txt`，从而把 reasoning 结果重新注入当前感知回路。

## 3. 当前 V2 的默认接入方式

当前设计下，V2 默认是：

**通过大模型 API 进行高层语义推理**

但要强调：

- API 接入点在 `reasoner`
- 不在底层控制环
- 不直接发布 `/falcon/pos_cmd`、`/ego/pos_cmd` 或 PX4 控制指令
- 所有建议都必须经过 `ReasonerGuard`

也就是说，当前 V2 是：

**API-based bounded runtime reasoner**

而不是：

**API-based action policy**

## 4. 当前 V2 还没有做完的部分

虽然 V2 已经开始落地，但目前仍属于初版，以下能力还没有做满：

1. `insert_verify_stage` 目前只在 guard/action schema 中预留，还没有真正实现动态插入验证阶段。
2. `ConsistencyVerifier` 仍然较轻，还没有和 LLM reasoner 做更深的 relation-aware 协同。
3. 还没有做更细的 reasoner trigger policy，例如按不同 stage intent 采用不同触发规则。
4. 还没有做本地模型后端，目前默认是 API backend 或 noop backend。
5. 还没有做线上 API 超时、失联时的更细降级策略。

## 5. 当前配置方式

在 [/home/young/uav_demo/central_runtime_v0/config.yaml](/home/young/uav_demo/central_runtime_v0/config.yaml) 中，已经新增了 `reasoner` 配置段。

默认状态：

- `enabled: false`
- `backend: noop`

这意味着：

- 默认不会真的调用大模型
- 当前代码会保留 reasoner 接口，但不影响 V1 runtime 的稳定运行

如果后续启用 API 版 V2，需要至少配置：

- `reasoner.enabled: true`
- `reasoner.backend: llm_api`
- `reasoner.model`
- 对应的环境变量，如 `OPENAI_API_KEY`

## 6. 当前阶段的意义

这一步的意义，不是立刻把系统变成“模型驱动”的 agent，而是先把：

- V1 的 verified runtime
- V2 的 bounded LLM reasoning

正式串到一起。

这样后续继续增强时，系统已经具备了清晰的结构边界：

- verifier 负责验证
- reasoner 负责解释与建议
- guard 负责约束
- executor 负责最终执行

# 几何语义与空间定位模块设计稿

## 1. 设计目标

本设计稿面向当前项目下一阶段的“空间语义增强”需求，目标是在不破坏现有 verified runtime 架构的前提下，为系统补充：

- 目标的相对坐标与世界坐标估计
- 几何语义证据
- 观察点 / 接近点生成
- 供 runtime 和大模型协同使用的空间状态

核心原则：

- 坐标解算交给几何模块，不交给大模型脑补
- 目标点生成尽量交给规则/几何模块，不直接让大模型输出 waypoint
- 大模型只做高层语义决策
- 需要硬件、标定、位姿解算才能完成的部分先预留接口，不硬实现

---

## 2. 总体思路

建议把空间语义链路拆成三层：

1. `Geometry Localizer`
- 输入：RGB mask / bbox、深度图、相机参数、外参、odom
- 输出：目标在机体系和世界系下的位置估计

2. `Viewpoint Planner`
- 输入：目标世界坐标、当前无人机 odom、任务模式、安全距离约束
- 输出：候选观察点 / 接近点 / 撤离点

3. `Runtime + LLM`
- runtime 维护空间状态、融合感知与几何证据
- LLM 只负责高层语义动作选择
- 例如：继续观察 / 进入 verify / 去安全出口 / 从左侧观察

一句话概括：

- 几何模块回答“目标在哪里”
- 规则模块回答“有哪些可去的位置”
- LLM 回答“此时应该选哪一类位置”

---

## 3. 推荐架构

### 3.1 新增模块

建议在 `central_runtime_v0/central_runtime/` 下新增：

- `geometry_context.py`
- `geometry_localizer.py`
- `viewpoint_planner.py`
- `spatial_state.py`

建议职责：

#### `geometry_context.py`
- 定义几何相关数据结构
- 例如：
  - `CameraIntrinsics`
  - `TransformSE3`
  - `TargetLocalization`
  - `ViewpointCandidate`

#### `geometry_localizer.py`
- 做 RGB mask / depth / odom 融合
- 输出目标 3D 定位结果

#### `viewpoint_planner.py`
- 根据目标位置和任务模式生成可用观测点

#### `spatial_state.py`
- 作为 `WorldState` 的空间子状态，供 runtime 和 reasoner 使用

## 4. Geometry Localizer 设计

## 4.1 输入

建议输入包括：

- 当前 RGB 图像中的目标 mask 或 bbox
- 同时间戳 depth image
- camera intrinsics
- camera-to-body extrinsics
- 当前 odom

建议数据结构：

```python
GeometryLocalizeRequest(
    t_wall: float,
    entity_id: str,
    bbox_xyxy: Optional[List[float]],
    mask: Optional[Any],
    depth_path: Optional[str],
    rgb_path: Optional[str],
    camera_frame: str,
    body_frame: str,
    world_frame: str,
    intrinsics: Optional[CameraIntrinsics],
    T_body_camera: Optional[TransformSE3],
    odom_pose: Optional[TransformSE3],
)
```

## 4.2 输出

建议输出：

```python
TargetLocalization(
    entity_id: str,
    status: str,  # localized / weak / failed
    t_wall: float,
    target_pos_camera: Optional[List[float]],
    target_pos_body: Optional[List[float]],
    target_pos_world: Optional[List[float]],
    localization_confidence: float,
    valid_depth_ratio: float,
    depth_median: Optional[float],
    covariance_hint: Dict[str, float],
    notes: Dict[str, Any],
)
```

## 4.3 最小实现策略

在不引入复杂点云算法的前提下，先做一个实用版：

1. 用 `mask` 或 `bbox` 选出目标像素区域
2. 在深度图中取：
- 中值深度
- 有效像素比例
3. 将目标中心点或 mask 质心投影到相机坐标系
4. 用外参转到机体系
5. 用 odom 转到世界系

这一步不求完美，但足以提供：

- 粗目标方位
- 粗距离
- 粗世界位置

## 4.4 能力边界

当前阶段 `geometry_localizer` 不建议承担：

- 稠密 3D 重建
- 多目标跟踪级数据关联
- 高精度 SLAM 级语义地图构建

当前阶段只做：

- 单目标几何定位
- 低频空间状态更新

## 5. Viewpoint Planner 设计

## 5.1 目标

不要直接让大模型根据坐标算 waypoint，而是由规则模块生成一组候选视点，再由 runtime / LLM 选策略。

## 5.2 输入

建议输入：

- 当前无人机 odom
- 目标世界坐标
- 当前任务模式
- 安全距离
- 观察距离
- 高度约束
- 地图边界或飞行约束

建议数据结构：

```python
ViewpointPlanRequest(
    entity_id: str,
    current_odom: Dict[str, Any],
    target_pos_world: List[float],
    mode: str,  # observe / approach / inspect / exit
    standoff_distance_m: float,
    preferred_altitude_m: Optional[float],
    min_altitude_m: Optional[float],
    max_altitude_m: Optional[float],
)
```

## 5.3 输出

建议输出候选 waypoint 集合：

```python
ViewpointCandidate(
    candidate_id: str,
    mode: str,
    xyz_world: List[float],
    yaw_world: Optional[float],
    score: float,
    notes: Dict[str, Any],
)
```

例如输出：

- `observe_front`
- `observe_left`
- `observe_right`
- `safe_standoff`
- `go_to_exit`

## 5.4 最小实现策略

先做规则生成，不做复杂优化：

- 以目标世界坐标为中心
- 按固定 standoff distance 生成左右前后几个候选点
- 高度优先保持当前高度或任务要求高度
- yaw 可以朝向目标

这一步已经足够让 runtime 和 LLM 利用。

---

## 6. LLM 在空间语义链路中的职责

## 6.1 建议让 LLM 做的事

LLM 可以基于以下信息做高层判断：

- 当前目标世界坐标
- 当前无人机位姿
- 目标定位置信度
- 候选观察点列表
- 当前任务阶段
- 当前 semantic verification 结果

然后输出：

- 是否继续观察
- 是否进入 verify stage
- 是否切换到某个观察模式
- 是否去出口
- 是否保持安全距离

## 6.2 不建议让 LLM 做的事

不建议直接让 LLM：

- 输入坐标后直接输出最终 odom waypoint
- 直接计算精确视角点
- 直接替代几何与规划算法

更建议的方式是：

- LLM 选动作模式
- `viewpoint_planner` 生成具体点
- runtime 选择并下发给 EGO

- 是否需要补观察
- 是否可以生成接近点
- 是否需要 fallback 到 SEARCH

## 8. 与现有模块的关系

## 8.1 与 GSAM2 的关系

GSAM2 提供：

- bbox / mask / proposal

几何模块利用这些 proposal 去做空间定位。

所以关系是：

- `GSAM2 -> Geometry Localizer`

而不是：

- `GSAM2 自己做 3D 空间理解`

## 8.2 与 Semantic Verifier 的关系

semantic verifier 不负责算坐标，但可以利用空间信息做更强解释：

- 目标距离是否合理
- cue 与 primary 是否空间上相容
- 当前观察是否足够

所以关系是：

- `Geometry -> Semantic Verification`

## 8.3 与 EGO 的关系

EGO 仍然是底层局部规划与轨迹执行模块。

几何语义模块只负责：

- 生成候选观察点
- 生成目标点

runtime 最终选定一个点后，仍通过现有 goal 接口发给 EGO。

## 11. 分阶段实施建议

## 11.1 第一阶段：接口预留

现在就可以做：

- 新增几何相关数据结构
- 预留 `geometry_localizer` 接口
- 预留 `viewpoint_planner` 接口
- 扩展 `WorldState`

## 11.2 第二阶段：软件模拟版

在没有硬件的情况下，可以先做：

- 用 fake depth / fake odom 或离线数据测试接口
- 验证 runtime 如何消费空间状态

## 11.3 第三阶段：硬件回归后接真数据

飞机恢复后再做：

- depth + odom 真正接入
- 坐标解算
- 候选视点生成
- 与 EGO 联调

---

## 12. 推荐下一步

当前最合适的下一步不是直接编码几何解算，而是：

1. 先把 `geometry_localizer / viewpoint_planner / spatial_state` 的接口层搭起来
2. 在 `WorldState` 中预留空间字段
3. 等硬件恢复后再填真数据链路

这样既不阻塞架构推进，也不会越过当前硬件条件。
